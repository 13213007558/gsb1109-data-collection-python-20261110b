Source location tracking
========================

HTML in the wild is frequently malformed.  When the tokenizer feeds the tree
builder, misplaced content is moved (for example text between table rows is
*foster parented* in front of the table) and missing containers such as
``<html>``, ``<head>`` and ``<tbody>`` are generated automatically.  The
``source_locator`` option records where every node of the resulting tree came
from in the original document, so an auditing or reviewing tool can map a node
on the final tree back to the page position it was written at.

The feature is opt-in and, when disabled, parsing behaves exactly as before
with no extra bookkeeping.

Enabling it
-----------

Construct the parser with ``source_locator=True``; after parsing, the
:class:`~html5lib.SourceLocator` is available as the parser's
``source_locator`` attribute::

    from html5lib import HTMLParser, SOURCE_ORIGIN_IMPLIED

    parser = HTMLParser(source_locator=True)
    document = parser.parse(source)
    locator = parser.source_locator

Three kinds of origin
---------------------

Each element, comment and doctype node has a
:class:`~html5lib.SourceInfo` distinguishing:

* **present** -- the node corresponds to markup or characters that were
  written in the input.  Its :class:`~html5lib.SourceLocation` spans the tag,
  comment or doctype in the normalized input.
* **implied** -- the node was generated by the parser during error recovery
  and has no markup of its own.  This covers the implied
  ``<html>``/``<head>``/``<body>``, implicit ``<tbody>``, reconstructed active
  formatting elements and the clones produced by the adoption agency
  algorithm.  An implied node has no location of its own.

Text is kept separately from the element it lives in, because an implied
container (e.g. an implied ``<body>``) can still hold real input text.  Use
:meth:`~html5lib.SourceLocator.textRangesOf` to obtain the ordered list of
:class:`~html5lib.SourceRange` objects that make up an element's text.  A
normal text node yields one range; text assembled from several pieces --
whitespace emitted as its own token, an expanded entity, or characters
recombined across table foster parenting -- yields one range per piece, each
with its own exact location and the characters it contributed.

Clicking a moved remark
-----------------------

Because the location is captured from the token before the tree builder moves
the node, foster-parented content still points at where it was authored::

    source = "<table><tr><td>cell</td></tr>REMARK<tr><td>x</td></tr></table>"
    parser = HTMLParser(source_locator=True)
    document = parser.parse(source)

    body = document.find(".//{http://www.w3.org/1999/xhtml}body")
    range_ = parser.source_locator.textRangesOf(body)[0]
    start, end = range_.location.startOffset, range_.location.endOffset
    assert source[start:end] == "REMARK"

The remark ends up before the table in the final tree, yet its range still
selects ``REMARK`` at its original position.

What the coordinates mean
-------------------------

All offsets and line/column numbers describe the **normalized character
stream** the tokenizer consumes, not the raw bytes handed to the parser:

* The stream is decoded using the encoding the parser settles on (BOM,
  transport or override encoding, ``<meta charset>``, or the default).
* A leading byte-order mark is consumed during encoding sniffing and is not
  part of the tracked stream.
* Line endings are normalized before tracking: ``CR LF`` and a lone ``CR``
  each become a single ``LF``.  A line is therefore always terminated by
  ``LF``, and a Windows or classic-Mac document gets the same coordinates as
  its LF-normalized equivalent.  Character offsets count normalized
  characters, so they are shorter than the raw count whenever ``CR``
  characters were removed.
* Offsets are zero-based code point indices; line numbers are one-based;
  columns are zero-based character columns measured from the end of the
  preceding ``LF``.  The end of a range is the offset/column one past the last
  character (half-open ranges).
* Surrogate pairs and combining marks count as individual code points.

When the declared encoding changes (a tentative encoding corrected by
``<meta charset>``) the input is re-read from the start; the locator is reset
and all reported coordinates refer to the final, correctly decoded stream.

To highlight the corresponding region of the original page, invert the
encoding and line-ending normalization and apply the same offset range.
